# 古着コーデ相談ボット (Furugi Coordinate Consultation Bot)

古着好きのためのAIスタイリスト。Dify + React で構築した、AIチャットボット機能を持つWebアプリケーションです。

ユーザーが手持ちのアイテムや予算、シーンを伝えると、90年代〜Y2K、アメカジ、ミリタリー、ワークウェア等の古着ならではのジャンル知識を活かしたコーディネート提案を返します。

## 主な機能

- 古着コーディネートに特化したAIチャット
- ユーザーの入力に対して、シーン・雰囲気・具体的なアイテム名を含む3案提案
- 会話文脈の保持(前の会話を踏まえた返答)
- ブラウザリロード後も会話履歴を継続(localStorage による永続化)
- 送信中のローディング表示、エラー時の視覚的フィードバック

## アーキテクチャ

### 通信フロー

- ユーザーのブラウザから React アプリ (Vite ビルド) にHTTPリクエスト
- React アプリから fetch API 経由で Dify Cloud API にリクエスト
- Dify Cloud API が GPT系モデルで LLM推論
- Dify → React → ブラウザ の経路で応答が返る

### 主要ファイル構成

- src/App.tsx — メインのReactコンポーネント、状態管理
- src/lib/difyClient.ts — Dify API通信の専用モジュール
- .env.local — 環境変数(APIキー、URL)※ Gitignore対象
- docs/ — 開発ドキュメント(フェーズごとの記録)

## セットアップ手順

このプロジェクトを、忘れた頃の自分や、初心者が再現できる粒度で記載します。

### 前提

- Node.js がインストール済み
- Git がインストール済み
- Dify アカウント作成済み、チャットボットアプリ作成済み、APIキー発行済み

### 手順

1. リポジトリを取得

```
git clone [リポジトリのURL]
cd furugi-chatbot
```

2. 依存パッケージのインストール

```
npm install
```

インストールには1〜3分かかります。

3. 環境変数の設定

プロジェクトのルート直下に .env.local ファイルを新規作成し、以下の内容を記述します。

```
VITE_DIFY_API_KEY=app-XXXXXXXXXXXXXXXXXX
VITE_DIFY_API_URL=https://api.dify.ai/v1
```

VITE_DIFY_API_KEY: Difyダッシュボードで発行したAPIキー(app- で始まる文字列)
VITE_DIFY_API_URL: Difyクラウド版の共通エンドポイントURL

注意事項:
- APIキーは絶対にGitHubにコミットしない(.gitignore の *.local パターンで自動除外されます)
- クォート(" や ')は不要
- = の前後にスペースを入れない
- APIキーはパスワード管理ツールで安全に保管することを推奨

4. 開発サーバー起動

```
npm run dev
```

http://localhost:5173/ にブラウザでアクセスして動作確認します。

5. 動作確認

チャット入力欄に「白いTシャツに合う古着のボトムスを教えてください」等を送信し、AIから具体的なコーディネート提案が返ってくれば成功です。

## 開発を通して

### この開発で得た主な学び: 「動くもの」と「本番運用に耐える設計」の距離

本プロジェクトでは、Dify APIをフロントエンドから直接呼び出す方式を採用しました。この判断の背景には、明確な意思決定があります。

選んだ方式(直接呼び出し)

フロントエンド(React)から Dify API に直接 fetch でリクエストを送る構成です。APIキーは .env.local に置き、Viteのビルド時にバンドルに埋め込まれます。実装がシンプルで、コードの流れが追いやすいのが利点です。

選ばなかった方式(バックエンド中継)

自前のバックエンドサーバー(例: FastAPI)を用意し、フロントエンドは中継サーバーを叩き、中継サーバーが Dify API を叩く構成です。APIキーはサーバー側の環境変数で管理され、フロントエンドには露出しません。

なぜ直接呼び出しを選んだか

- 学習・課題スコープ内で完結する
- 実装がシンプルで、コアの技術要素(API連携、状態管理、永続化)に集中できる
- 個人学習用途としては、.gitignore で .env.local を除外する運用で十分

本番運用時の切り替え方針

商用サービスとして提供する場合、直接呼び出し方式には以下の課題があります。

- ビルド後のJSファイルを見ればAPIキーが取得可能(発行者に課金が及ぶリスク)
- 顧客ごとのAPIキー管理・課金分離が難しい
- リクエスト制限や利用ログ管理が困難

これらを解決するため、本番運用時はバックエンド中継サーバー方式に切り替える設計思想を持っています。既存のアーキテクチャは、フロントエンドの通信先URLを変更するだけで移行できるよう、疎結合な構造にしています。

この判断が意味すること

「動くもの」と「本番運用に耐える設計」の間には、明確な距離があります。今回の選択は、その距離を意識した上で、「今のスコープでは直接呼び出しで十分」と判断した結果です。学習フェーズでは実装のシンプルさを優先し、本番フェーズでは設計を切り替える、という段階的な移行を前提とした設計をしています。

エンジニアリングは「動かすこと」と「動かし続けること」の両方が必要で、その距離を意識的に埋めていくことが実務の本質だと理解しました。
