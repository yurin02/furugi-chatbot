# 04: サンプル質問ボタンの追加

## このフェーズでやったこと

会話開始前のチャット画面に、タップするだけで質問を送信できる「サンプル質問ボタン」を追加した。API連携が完了した状態のアプリに、UXを改善する機能を1つ足すフェーズ。

## 機能仕様

### 表示条件
- `messages`配列にユーザー送信メッセージ(`sender: 'me'`)が1件も無い状態でのみ表示
- ユーザーが1回でも送信したら、以降は非表示
- `messages`はlocalStorageに永続化されているため、リロード後も「未送信状態が続いている限り」再表示される(逆に言えば、一度送信済みの状態でリロードしても再表示されない。これは仕様通り)

### ボタン押下時の動作
- 対応する質問文がユーザーメッセージとして送信される
- 既存の`sendMessage`関数をそのまま再利用(通常の入力欄からの送信と同じAPI呼び出しフローに乗る)
- ボタン群は消え、次回会話をリセットするまで再表示されない

### サンプル質問の内容(6件)
- 白いTシャツに合う古着のボトムスを教えて
- 秋のデートにおすすめの古着コーデを3案
- 30代男性のカジュアル古着スタイル
- 予算1万円で作れる古着コーデ
- 初めての古着挑戦、何から始めるべき？
- 90年代っぽさを出せる古着アイテムは？

## 実装

### 設計判断: ファイル分割
質問データとUIコンポーネントを、それぞれ専用ファイルに切り出した。

- `src/data/sampleQuestions.ts` — 質問文の配列のみを保持。文言を変更したい場合はこのファイルだけ触ればよい
- `src/components/SampleQuestions.tsx` — ボタン群のUIコンポーネント。`onSelect`(選択時のコールバック)と`disabled`(送信中フラグ)をpropsで受け取る
- `src/App.tsx` — 上記2つを利用する側。表示条件の判定(`hasUserSent`)と送信ロジックの呼び出しのみを担当

「UIコンポーネント」「データ」「状態管理」を分離した理由は、API連携部分(`src/lib/difyClient.ts`)で既に採用していた「関心の分離」の考え方([[03-api-integration.md]]参照)を今回も踏襲したもの。

### 既存ロジックの再利用
`sendMessage`関数に`overrideText?: string`という省略可能な引数を追加し、`(overrideText ?? input).trim()`で「入力欄の内容」と「ボタンから渡された質問文」の両方に対応できるようにした。ボタン専用の送信関数を新たに作らないことで、エラー処理・localStorage永続化・conversation_id更新のロジックが1箇所に保たれている。

### アクセシビリティ配慮
ボタンの高さは`min-h-11`(44px)を明示し、スマホでもタップしやすいサイズを確保した。

## 動作確認チェックリストと結果

以下の項目を、開発者ツールで`localStorage.clear()`した上で(初期状態を再現した上で)確認した。全て問題なしとの回答を得た(2026-09-02)。

1. **初期表示**: ページを開いた直後、Botの挨拶2件の下に「こんな質問はいかがですか？」の見出しとサンプル質問ボタン6個が表示されるか → OK
2. **ボタン押下**: いずれかのボタンを押すと、その質問文がユーザーメッセージとして送信され、「入力中...」→Difyからの返答、という通常フローが動くか → OK
3. **ボタン群の非表示**: 送信後、ボタン群が消えて再表示されないか → OK
4. **リロード後の継続**: 送信済みの状態でリロードし、ボタン群が再表示されない(会話が続いている)ことを確認 → OK
5. **新規タブ/シークレットウィンドウ**: localStorageが空の状態でアクセスし、初期表示でボタンが出ることを確認(未送信状態の再現) → OK

### エッジケース
- ボタンを連打した場合、2件以上のメッセージが二重送信されないか(`disabled={isSending}`で送信中は無効化される想定) → 想定通り
- テキスト入力欄に文字を打ちかけている途中でサンプルボタンを押すとどうなるか(入力欄の内容は送信されず、ボタンの質問文が優先される想定) → 想定通り
- スマホ幅(狭い画面)でボタンが1列になり、タップしやすいサイズになっているか → OK(`grid-cols-1 sm:grid-cols-2`で対応)

補足: このチェックリストは自動テストコード化はしておらず、手動確認のみで完結している。

## 詰まったポイント

### 開発サーバーのポートずれで別プロジェクトが表示された
動作確認のために`http://localhost:5173/`を開いたところ、furugi-chatbotではなく以前取り組んだ別課題の画面が表示された。原因は、複数プロジェクトの`npm run dev`を止め忘れたまま並行して動かしていたため、5173番ポートを別プロジェクトが先に占有し、furugi-chatbotは5174/5175番に自動で回されていたこと。`netstat -ano`でポートを握っているPIDを特定し、`Get-CimInstance Win32_Process`でコマンドラインを確認して原因を特定、該当プロセスを停止して5173番で再起動した。詳細な再発防止策は dev-knowledge の pitfalls に記録済み。

### localStorage永続化を「バグ」と誤解した
サンプル質問ボタンは仕様上「一度送信したら以降非表示」だが、動作確認時に既に1件送信済みの状態が残っていたため、リロードしてもボタンが再表示されず、一見バグのように見えた。実際はlocalStorageに会話状態が永続化されているための正常な挙動。動作確認を依頼する際は、事前に「localStorage.clear()してから試す」よう明記すべきだったという教訓を得た。

### README.mdがポートフォリオとして分かりにくかった
機能追加後、README.mdの「デモ」セクションの写真が機能追加前(2026-08-04撮影)のままで、本文に書いた新機能が写真に写っていない齟齬があった。新しいスクリーンショットに差し替えて解消した。また、想定読者に非エンジニア(人事・経営層等)も含まれることが分かったため、冒頭に平易な一言要約を追加し、専門用語の多いセクションには「読み飛ばしてよい」旨の前置きを追加した。

## 未対応・今後の課題

- **AIの回答にMarkdown記法の記号(`**`や`##`等)がそのまま表示される問題**: Difyが返す回答がMarkdown形式で書かれているが、アプリ側でレンダリングしていないため生の記号が見える。対応方法として、(A) `react-markdown`等でフロントエンド側できちんと描画する、(B) Dify側のシステムプロンプトで「Markdown記法を使わず平文で回答する」よう指示する、の2案を検討済み。この時点では未着手。
