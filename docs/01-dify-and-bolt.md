# 01: Difyアプリ作成〜BoltでUI完成まで

## このフェーズでやったこと

Difyで古着コーデ相談ボット用のチャットフローを新規作成し、Bolt.newで段階的にチャットUIを構築した。BoltからCursorへ移行する前段階のフェーズ。

## Difyでの作業

### 新規アプリ作成の判断
既存の「経費ボット」のAPIキーを流用する選択肢もあったが、以下の理由で新規アプリを作成することにした。

- 経費ボット流用ではレシート画像を投げないと真価が出ず、テキストチャットのデモとしては地味になる
- 利用量(トークン消費)を用途別に分離して把握したい
- Difyのアプリ作成〜APIキー発行の一連の流れを、B2B事業への布石として繰り返し身につけたい

### アプリ設計
- タイプ: チャットフロー
- アプリ名: 古着コーデ相談ボット
- モデル: gpt-5.5
- システムプロンプトで「古着コーディネート専門アドバイザー」としての人格を明示的に定義

### システムプロンプトのポイント
以下の3点を意識して設計した。

1. 役割の明示 — 90年代〜Y2K、アメカジ、ミリタリー、ワークウェア等の古着ジャンル知識を活かすことを指示
2. 回答スタイル — 結論から先に伝える、3案提案する、曖昧なら1つだけ聞き返す
3. 禁止事項 — ハイブランド新品購入を勧めない、曖昧回答で逃げない

### APIキー発行
アプリを「公開」した後、APIアクセス画面から新しいシークレットキー(app-で始まる文字列)を発行。API サーバーURL(https://api.dify.ai/v1)と合わせて Bitwarden に保存した。

保存時のポイントとして、単にキーを保存するだけでなく、どのDifyアプリのキーなのかを明記した(以前、経費ボット用のキーとの混同が起きたため)。

## Boltでの作業

### UI作成のアプローチ
Boltには一度に全部指示するのではなく、3段階のプロンプトに分けて指示した。理由は以下。

- 途中でエラーが出た時の原因特定がしやすい
- 各段階の動作確認ができる
- Boltが生成するコードのクセを段階的に把握できる

### Prompt 1: 最小のチャットUI
Vite + React + TypeScript + Tailwind CSSの構成で、メッセージ一覧、入力欄、送信ボタンだけのシンプルなUI。API連携なしのダミー動作。

### Prompt 2: デザインと機能の調整
- ユーザー右寄せ青、Bot左寄せグレーの吹き出し
- ヘッダー「古着コーデ相談」
- 自動スクロール、空欄送信の無効化

想定と実際の差として、Prompt 1の時点でBoltが既にユーザー右寄せ青・Bot左寄せの実装を先取りしていた。「変わっていない」ではなく「既に満たされていた」というのが正しい理解だった。

### Prompt 3: API連携準備
- 送信中の状態管理(送信ボタン・入力欄の無効化、「入力中...」表示)
- エラー表示エリアの追加
- 送信ロジックを関数として切り出し(後でAPI呼び出しに差し替えやすい構造)
- setTimeout で1秒の遅延を入れて、ローディング状態を目視確認できるように

## 詰まったポイント

### Bolt無料プランのトークン枯渇
本垢yurin02のGitHubに紐付いたBoltアカウントで作業を進めていたが、途中で「You've used all your tokens」の表示が出て新規生成ができなくなった。

対処法として以下を検討した。
- 別垢で新規登録して継続 → 後でリポジトリ移し替えの手間が発生
- 24時間待って本垢のトークン回復を待つ → 確実だが時間ロス
- 有料プラン加入 → 費用対効果が悪い

結果として、48時間後に本垢のトークンが回復していたので、本垢で最初から作り直す形で完走した。教訓は「アカウントを一元化した方が管理が楽」。

### プレビュー入力欄と Bolt 指示欄の混同
Prompt 2 を Bolt の指示欄ではなく、右側プレビューのチャットUI入力欄に貼り付けてしまうミスがあった。結果、プロンプトの内容がそのままダミーBotへの送信メッセージとして表示された。

Boltの画面は「左側=Boltへの指示欄」「右側=作ったアプリのプレビュー」の2つの入力欄があるため、明確に区別する必要がある。

### GitHub push後の画面反映遅延
Boltから GitHub にpushした際、Bolt側の画面表示が「作業中」のまま変わらず、失敗したように見えた。実際には裏で正常にpushされており、GitHub側で直接確認したところ11分前のタイムスタンプで正常にリポジトリが作成されていた。

教訓として、ツールの画面表示に頼らず、実データ(この場合はGitHub側)で確認するのが確実。
